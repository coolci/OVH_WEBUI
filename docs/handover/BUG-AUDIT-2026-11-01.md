# OVH_WEBUI 代码审计 — 2026-11-01

只读审计，未改业务源码，未跑全量测试，未执行真实 OVH 写操作。范围是当前工作区源码：购买与队列、监控、鉴权、Telegram、独服/VPS 控制，以及对应前端。

对照 2026-10-13 逻辑校对（L01–L10）：入队先落库、网页暂停会取消进行中的请求、VPS 监控启停死锁、VPS 自动下单硬拦截、跨账户去重、422 重复建账户、VPS 别名串户、登录限流不再盲信 `X-Forwarded-For`，这些在当前源码里仍然成立。下文是这次新确认的问题。

## 结论

有 8 项会直接导致多买、买错机器或重装时动错磁盘，应先处理。另有 8 项在特定操作下会下错单、串账户或把密钥带回浏览器。

| 级别 | 数量 | 含义 |
|------|------|------|
| P1 | 8 | 当前路径上会多下单、认错订单、暂停后仍结账，或重装参数丢失 |
| P2 | 8 | 需要特定操作才会触发，仍然会下错单或泄密 |

## P1

### 1. 监控验价抖动会在已有任务未完成时再入一单

监控把「有货 → 验价失败 → 再有货」当成新的补货。

- `backend/internal/monitor/check.go`：`oldStatus == "price_check_failed"` 且本轮可用时进入 `orderTargets`（约 588–592 行、705–710 行）。
- `backend/internal/monitor/loop.go` 约 341 行对监控入队设置 `SkipDuplicateCheck: true`。
- `backend/internal/purchase/quick_order.go` 约 167–184 行因此跳过「队列里已有同配置 running / pending / paused 任务」的检查。
- `backend/internal/app/automatic_order.go` 约 78–81 行只拦住已暂停的任务，不拦正在跑的任务。
- 120 秒闸门只认历史里的 `success`。

触发：自动下单已入队、任务还在重试；某一轮 OVH 429 或询价超时把状态打成 `price_check_failed`，下一轮验价通过。同一型号、同一机房会再入一条 running 任务，两条都会结账。`autoPay` 打开时就是扣两次。

### 2. 结账超时对账会把别的任务的订单认成自己的

`backend/internal/purchase/reconcile.go` 约 89–110 行、156–164 行：对账只要求订单明细文本里包含 `planCode`，不看机房、配置，也不排除历史里已经记下的订单号。

触发：监控一次补货按「机房 × 数量」并发入队（`loop.go` 的 `batchOrder`）。任务 A 已经结账成功，任务 B 的 checkout 超时。B 的对账扫到 A 的订单，把 B 标成成功。结果是少买一台，历史里两笔任务共用一个订单号。若对账没扫到、任务按失败重试，则可能多买一台。

### 3. 结账结果不确定之后，暂停挡不住重启和人工恢复

`backend/internal/purchase/purchase.go` 约 597–622 行：checkout 超时且对账无结论时，先 `recordFailure`（历史是失败、没有订单号），再要求暂停，并通知用户去 OVH 后台看有没有未付款订单。

`backend/internal/purchase/queue_processor.go` 约 303–316 行把状态改成 `paused` 后如果 `SaveQueue` 失败，只打日志。重启后库里仍是 `running`。`RestoreCompletedQueue` 只认「成功且有订单号」，不会拦住这种失败记录。用户在队列页把任务改回运行（`handlers/queue.go` 约 230–258 行）同样不会再对账。

OVH 上如果第一笔其实已经生成，下一次结账就是第二台。`autoPay` 打开时会再扣一笔。

### 4. 代理熔断只改状态，不取消已经在跑的下单

`backend/internal/proxyguard/proxyguard.go` 约 227–240 行把该账户任务标成 `paused`，没有调用 `CancelTask`。结账前的最后一道检查在 `purchase.go` 约 555–557 行，只看 `ctx` 是否取消和任务是否标记删除。`app.go` 约 657 行的 `IsTaskActiveInQueue` 能识别暂停，全仓库没有任何调用。

触发：购物车还在加配置时，该账户代理连续失败，看门狗通知「已暂停」。这一轮请求的 context 没被取消，结账仍会发出。网页上点暂停走的是 `handlers/queue.go` 里的 `UnregisterTaskCancel`，那条路径会拦住。

### 5. 退出和 Windows 自更新不会停抢购循环

`backend/internal/purchase/queue_processor.go` 约 124–126 行使用 `context.Background()`。`backend/internal/worker/supervisor.go` 的 `Stop` 只停 Telegram 轮询、独服监控和 VPS 监控。`backend/internal/server/shutdown.go` 的日志写的是后台循环已停止，随后就关数据库。

`backend/internal/server/server.go` 的 `GracefulRestart` 不调用 `Supervisor.Stop`。Windows 的 `updater/install_windows.go` 先 `cmd.Start()` 新进程，再 `os.Exit`。新进程会再起一个 `ProcessQueueLoop`，旧进程里的结账可能还在飞。两个进程对同一批 `running` 任务各下一单。Docker `restart: unless-stopped` 收到 SIGTERM 时也是同一类窗口。

### 6. 快速下单用的是另一个账户的目录和库存

`src/components/orders/QuickOrderDialog.tsx` 约 62–63 行调用 `useServers()` 和 `useAvailability()`，都没有传入弹窗里选的账户。这两个 hook 默认跟「独服当前账户」走（`src/hooks/ovh/use-servers.ts` 约 51–54 行，`src/hooks/ovh/use-availability.ts` 约 47–49 行）。提交时用的是弹窗里的 `account_id`（约 198 行）。

`useAvailability` 的注释写明：抢购对话框另选账户时必须传 `endpointOverride`。这里没传。独服账户在欧洲、弹窗选了美国账户时，列表、机房红绿点和选项都是欧洲的，单下到美国账户上。

### 7. 软 RAID 磁盘数量在分区组创建之前写入，实际不会发出

`src/hooks/ovh/server-control/use-server-install.ts` 约 90–94 行，在 `groups` 仍为空时查找默认磁盘组并写入 `partitioning.disks`。真正 `groups.set` 在约 95 行之后的 `partitions.forEach`。`g0` 始终是空的，用户填的磁盘数被丢掉。OVH 按默认（通常是全部磁盘）重装，可能清掉不该动的盘。

### 8. Telegram 选配置的 token 可重复使用

`backend/internal/handlers/telegram_wizard.go` 约 112–149 行用 `getCfgOffer` 读配置。`telegram_wizard_session.go` 约 334–342 行只读不删。同一条消息里连点两次配置（或点两个配置），轮询是串行的，两次都会 `ProcessOrder` 或 `enqueueWizardDCs`。窄配置那条路径用的是 `takeNarrowOffer`，点一次就失效。这条没有。

## P2

### 9. VPS 重装的 SSH 密钥列表来自独服账户

`src/hooks/ovh/use-active-account.ts` 第 95 行把 `useActiveAccount` 定义成独服账户。`src/components/vps-control/VpsReinstallDialog.tsx` 约 34–35 行用它拉 SSH 密钥。重装请求走 `/vps-control`，拦截器注入的是 VPS 账户。两个账户不同时，提交的是独服账户里的密钥名。VPS 账户上同名密钥会被装上去，没有同名密钥则重装失败。

### 10. 设置接口把 Telegram Token 和旧 OVH 凭据原样返回

`backend/internal/handlers/settings.go` 第 19 行直接返回 `state.Config.Get()`。`types.Config` 含 `tgToken`、`appKey`、`appSecret`、`consumerKey`，读配置时已解密。账户列表会打码，设置接口不会。拿到 API 密钥的人（或浏览器侧脚本）能拿走 Bot Token。

### 11. 优惠码被拒绝后仍按原价结账

`backend/internal/purchase/purchase.go` 约 541–546 行：OVH 明确拒绝优惠码（4xx）时只记一条警告，然后继续 checkout。`autoPay` 打开时按原价扣款。通知和购买历史里会带 `couponWarning`，扣款已经发生。

### 12. 上架按钮的内存回退路径点一次不会作废

新按钮会写入数据库，认领是一次性的。数据库写入失败时，`backend/internal/monitor/subscriptions.go` 约 424–428 行仍留在内存缓存里。`sniper` / `queue_all` 走 `telegram_wizard_actions.go` 约 196–204 行，`MessageUUIDCacheLookup` 之后没有 `MessageUUIDCacheDelete`。旧的 `add_to_queue` 路径在 `telegram.go` 约 198–200 行会删。数据库没写上时，同一颗按钮可以多次入队。

### 13. 「全部机房」在没有合法机房时改用固定机房表

`backend/internal/handlers/telegram_wizard.go` 约 411–417 行：`validAndInStockDCs` 为空时，`targetDCs` 换成 `telegram.StandardDCs`，然后入队。用户点的是「全部机房」，此时目录里没有可售机房，仍会为标准机房列表各建一条抢购任务。旁边的「全选有货」（约 398–401 行）在无货时会拒绝，这条不会。

### 14. 批量订阅整份目录并打开自动下单

`backend/internal/handlers/monitor.go` 约 198–199 行：`batch-add-all` 对每个在售型号调用 `AddSubscription`，机房和配置都是空。`monitor/types.go` 里空配置的含义是盯该型号的全部硬件配置。请求体里的 `autoOrder: true` 会原样保存。一次操作可以让整个目录在补货时按「配置数 × 机房数 × 数量」入队。单条订阅界面的数量上限是 100，批量接口这里没有再收紧。

### 15. 切换独服账户时，账户资料可能写进旧缓存

别名查询已经把账户 ID 放进请求参数。`src/hooks/ovh/use-account.ts` 里账户信息、订单、退款的 `queryKey` 带旧账户，请求本身不带 `account`，靠拦截器读 localStorage。`use-active-account.ts` 先改 localStorage 再 `invalidateQueries`。切换瞬间，新账户的 `/me` 数据会写入旧账户的缓存键。订单和实名信息会短暂（或在刷新失败时持续）串户。

### 16. 通知 Webhook 可以打到内网

`backend/internal/handlers/settings.go` 约 44–50 行只校验 `http` / `https` 和非空 host。通知发送没有拦截 `127.0.0.1`、链路本地和云元数据地址。已登录用户把 Webhook 设成内网地址后，补货或测试通知会由服务器代为 POST。

## 2026-10-13 项的复核

| 项 | 现状 |
|----|------|
| L01 入队失败后仍结账 | 先写库再发布，删除会 `MarkTaskDeleted` |
| L02 网页暂停后仍结账 | `queue.go` 在持有队列锁时 `UnregisterTaskCancel`。代理熔断那条路没有，见问题 4 |
| L03 VPS 启停死锁 | `Start` 在 `runningMu` 外面等上一代循环 |
| L04 VPS 自动下单 | `PurchaseVPS` 和 `autoOrderOnRestock` 直接返回。批量添加接口仍会把 `autoOrder` 存进库，当前循环不会调用购买函数 |
| L05 去重漏账户 | 快速下单和 Telegram 的比较里有 `AccountID` |
| L06–L08 | 422 重试、VPS 别名、别名缓存已按账户分开。账户资料缓存仍会串，见问题 15 |
| L09 登录限流 | 计数用 `ClientIP()`，未配置可信代理时不读伪造的转发头。反代后如果没设 `TRUSTED_PROXIES`，所有客户端仍共用代理 IP |
| L10 配对地址 | 优先 `PUBLIC_BASE_URL`。没配时仍可能按请求的 TLS 情况生成 `http://` |

## 建议处理顺序

1. 监控入队重新检查「同账户、同型号、同机房、同配置」是否已有 running 任务。验价抖动不要当成新补货。
2. 对账绑定本任务的机房和配置，并排除已经记在历史里的订单号。结账不确定时不要把「可恢复运行」当成安全默认。
3. `Supervisor.Stop` 取消 `ProcessQueueLoop`。自更新先停循环，再关库，再拉起新进程。代理熔断和网页暂停走同一条 `CancelTask`。
4. 快速下单的目录和库存改成弹窗所选账户。软 RAID 的 `disks` 放到 `groups` 建完之后再写。
5. Telegram 配置 token 用一次即删。
