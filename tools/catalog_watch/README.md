# 独立目录差异检测与待付款下单脚本

> 2026-11-07：服务器列表已内置默认开启的独立检测功能。不要与本脚本的 `--execute` 模式同时运行，两者没有共享去重记录。内置功能使用绑定的默认账户，按 planCode × 硬件/网络配置 × 机房各成功 1 台计数，最多 100 个任务并发；本脚本默认面向销售地区匹配的所有账户，按账户 × 配置 × 机房计数。两者均关闭自动付款。

入口：`tools/catalog_watch/watch.py`。Python 3.10+，只使用标准库。

检测是独立进程，不依赖浏览器，不读取前端 120 秒缓存。建单通过现有后端 `/api/queue/quick-order`，复用真实购物车的价格/配置校验、队列下单和结账对账。因此后端必须运行；这不是完全脱离后端的第二套 OVH 结账实现。

## 运行行为

- 默认每 **2 秒**开始一轮官方销售目录请求，`--interval 1` 可设为 1 秒。一次只保留一个目录请求；下载/解析较慢时不会堆积并发请求，秒级周期不代表保证秒级获取或完成订单。
- 每进程监控一个销售子公司，例如 IE、US、CA。按代码现有 EU/CA/US 归属表选择官方接口。
- 支持服务端返回的 ETag / Last-Modified 条件请求；请求携带 `Cache-Control: no-cache`，不能承诺绕过 OVH 自身的缓存。429/网络错误退避，并遵守 Retry-After。
- 可只读导入现有应用 SQLite 的 `catalogs` 表作为第一次比较基线，**不改动原数据库或网页缓存**。以后使用脚本自己的基线，不会被网页刷新覆盖。
- 没提供本地基线时，第一次成功拉取只建立基线，**不会对已有全目录下单**。
- 新 planCode、新 addon 组合、新增可选机房生成候选；删除、价格、说明文字、JSON 排序变化不生成候选。
- 配置严格按官方 `exclusive` / `mandatory` 分组展开，互斥配置分别下单；可选组含“不选”分支。候选进入现有后端购物车校验，非法组合不会因为检测到目录变化就直接结账。
- 默认使用销售子公司、endpoint 均匹配的所有已配置账户；可重复传 `--account` 固定账户。每账户 × 每组合 × 每机房 **1 台**。
- 所有提交硬编码 `autoPay=false`，不提供开启自动付款的参数。成功建单后由现有系统显示待付款订单；脚本记录 `accepted` 仅表示任务已入队，不等于 OVH 已建单。
- 独立提交线程处理持久化 outbox，慢速下单不会阻塞目录检测。当前提交线程为一个，后端真实询价本身也存在串行锁；大批组合不会全部在同一秒完成建单。
- 已提交组合持久化去重，重启不会重复提交。被现有队列或近期订单去重拦截时记录 `existing`，不绕过后端保护。
- 请求超时或结果不确定记录 `uncertain`，自动查询队列核对。没有证据时保留未决状态，**不会盲目再次提交**。如任务已从后端清除，则需要人工核对，不能承诺无证据自动恢复。
- 单实例文件锁避免同一个状态库被两个检测器同时使用。不同状态文件不能互相去重，因此不要为同一销售地区同时启用多个执行实例。
- 目录为空、异常缩减超过 20%、缺少机房或组合过多时保留原基线并记录错误。每机型默认展开上限 10000，可用 `--max-combinations` 调整；超限整机型延后处理，不静默截断组合。
- 这是**销售目录新增项检测**，不是已有配置补货监控。它不会把库存变化、价格变化都当新品，也没有恢复之前停用的“预售本地预订、等待目录上架”逻辑。

## 启动

在仓库根目录运行。将环境变量 `API_SECRET_KEY` 设置为现有后端 API 密钥，不要把真实值写进脚本或提交到 Git。

先模拟检查（只写独立状态库，不建单）：

```powershell
python tools/catalog_watch/watch.py --subsidiary IE --state tools/catalog_watch/dry-ie.db --baseline-db "实际应用数据库路径" --once
```

持续模拟监控：去掉 `--once`。

执行模式（真实创建待付款下单任务，不自动付款）：

```powershell
python tools/catalog_watch/watch.py --subsidiary IE --state tools/catalog_watch/live-ie.db --baseline-db "实际应用数据库路径" --interval 2 --execute
```

如后端地址不是默认值，加 `--base http://127.0.0.1:实际端口`。限定账户可加 `--account 账户ID1 --account 账户ID2`。不同销售子公司各运行一个实例，各用自己的状态文件。

dry-run 和 execute 必须使用不同状态库，脚本禁止悄悄将历史模拟任务转换成真实订单。后续重启继续使用原来的 live 状态库；不要删除它来“清缓存”，否则会丢失跨重启去重记录。

Ctrl+C 停止检测和新提交。**已经被后端接受的抢购任务仍由后端运行**，可在网页队列里暂停或删除。

状态库 `jobs` 的 `status/detail` 保存每个候选的进度，`payload` 保存 planCode、账户、机房与 options；不保存 API 密钥。`planned`=模拟、`pending`=等待提交/明确失败后重试、`accepted`=已入队、`existing`=已有同配置任务、`blocked`=认证/路由问题、`uncertain`=结果待核对。

## 验证

```powershell
python -m unittest discover -s tools/catalog_watch -p test_*.py -v
```

测试使用内存夹具、临时 SQLite 和本地模拟 HTTP 服务；覆盖新机型/配置、多账户多机房、互斥配置、无关变更、基线只读、模式隔离、重启去重、超时核对、失败重试、单实例锁及最终 HTTP 请求关闭付款。已加入 `npm run test:unit:tooling`。

开发时仅对官方 IE 目录做了一次只读结构核验；没有启动真实执行实例，没有进行真实建单或付款验证。

配置范围：硬件、带宽、vRack 等机器选项；可选的 `application-license` / `distribution-license`（Windows、SQL、cPanel 等软件许可）不作为自动新增配置，不枚举这些许可的叠加组合。若目录要求必选软件许可则停止该次自动解析并报告。
